# cleanTMLE 0.5.0, item P1: time zero, eligibility and variable timing

Design, 2026-10-18. Written from the brief, the approved inventory (`rescueCo/deviations_inventory.csv`) and decisions D1 to D11 (`2026-10-18-outcome-blind-design-stage.md`); Andrew chose to skip the brainstorming questions. Calls made without him are marked **[call]**.

## 1. Why

cleanTMLE 0.4.1 grades estimability: whether an estimator can recover a declared estimand if identification holds. It has no notion of when a variable was measured. The lock refuses outcome columns by exact name only (`R/lock.R:41-44`), so a covariate recorded after treatment, a column from the follow-up interview, or an eligibility rule applied after treatment all pass silently. In the unblinded Rescue.Co analysis these account for ten of the inventory's rows coded D or S: payment recorded at disposition (row 13), arrival physiology (14), the hospital reached and the distance to it (15), arrival-time covariates (11), covariates from the follow-up call (10), the adjustment set for times measured from injury (16), the exclusion of transfers, which depends on route (3), the six-month horizon counted from arrival (30), enrolment on arriving alive (I1) and time zero stated three ways (I2).

P1 makes the plan and the lock state time zero and the timing of every locked column, refuses the combinations that cannot identify a total effect, and requires a declared response to every identification flag. The dossier shows the result as an identification table in the style of the TARGET statement (`cashinTransparentReportingObservational2025`).

These checks were designed after the unblinded analysis found the problems. To guard against hindsight, each check is generic: it runs in every study, on every locked column, whether or not anyone suspects a problem, and it has no tuning threshold that could be set to fit Rescue.Co. The paper says how the checks came about.

## 2. Goals, non-goals, anti-goals

**Goals.**
- Time zero is declared in the plan, with the event from which follow-up is counted.
- Every column the lock keeps has a dictionary row: where it was recorded, when it was recorded and when the attribute it describes was fixed, both relative to time zero, and its role.
- The lock refuses what cannot be fixed by a declaration, and flags what needs a declared response.
- The dossier and the Muntner log show every flag with its response.
- `R CMD check` stays clean.

**Non-goals.**
- How the outcome is observed (P2). P1 only defines the dictionary roles P2 will use (`after_treatment`, `observation`) and keeps such columns out of the adjustment set.
- Several comparisons and restriction rungs (P3), tolerances and gates (P4), and the bias analysis for selection after time zero (P5, registered outside the package per D1).
- Checking that the declared timings are true. The package cannot know when a form was filled in; it makes the analyst say so, in a hashed record, before outcomes, and shows the consequences.

**Anti-goals.** P1 fails, even if it runs, if:
- the dictionary can be skipped, so the check runs only when someone suspects the problem;
- it adds a new exported function, against the ground rule;
- it lets a covariate fixed after time zero into the adjustment set without a reason and a named sensitivity analysis;
- the identification table reads as a verdict that identification holds. It lists what was declared and flagged; it does not grade identification.

## 3. Interface

### 3.1 `analysis_plan()`: two new arguments

```r
analysis_plan(...,
  time_zero = list(event = "transport decision",  # required: when treatment is assigned
                   measured_as = "time of injury", # optional: the proxy the data index on
                   follow_up_from = "arrival",     # optional; default = event
                   response = "..."),              # required when follow_up_from differs
  eligibility = list(                              # optional
    arrived_alive = list(description = "Arrived alive at a participating hospital",
                         assessed = "after",       # before | at | after time zero
                         response = "..."),        # required when assessed = "after"
    ...))
```

- `time_zero` is required **[call]**. A single string is accepted as `list(event = <string>)`.
- Time zero is the moment treatment is assigned, as in a target trial, where eligibility, assignment and the start of follow-up coincide (`hernan2016`) **[call]**. "Before" in the dictionary means before assignment; "at" means at assignment. The treatment's own row must therefore be `fixed = "at"`, and the lock refuses any other value (rule 6 below). When the data can only index time zero on a proxy, the plan says so in an optional `measured_as`, shown in the identification table. For Rescue.Co: `event = "transport decision (dispatch, or departure from the scene)"`, `measured_as = "time of injury, because arrivals by other means have no dispatch time"`, `follow_up_from = "arrival"`.
- `follow_up_from` names the event from which the outcome's follow-up is counted. If it differs from `event`, the plan stops unless `response` is given. This catches I2 (injury in the report, arrival in the code) and row 30.
- `eligibility` lists the criteria that formed the cohort, each with when it was assessed relative to time zero. A criterion assessed after time zero stops the plan unless it has a `response`. Criteria are text: the cohort is built before the lock, so the package cannot evaluate them; it records them.
- Both are part of the plan, so they are hashed into the lock and shown in the dossier's plan table.

### 3.2 `create_analysis_lock()`: one new argument

```r
create_analysis_lock(design_data, treatment, covariates, plan, id = "id",
                     dictionary)                   # required [call]
```

`dictionary` is a data frame with one row per column the lock keeps (id, treatment, covariates, negative controls, restriction variables, and any column with role `after_treatment` or `observation`):

| Field | Values | Meaning |
|---|---|---|
| `column` | a column of `design_data` | One row per column; a dummy-coded variable has one row per dummy |
| `variable` | text | The variable the column comes from, so the dummies of one variable group in the dossier |
| `source` | text | The form or file it was recorded on |
| `follow_up` | `TRUE` / `FALSE` | Recorded only for patients reached at follow-up |
| `recorded` | `before` / `at` / `after` | When the value was recorded, relative to time zero |
| `fixed` | `before` / `at` / `after` | When the attribute it describes was fixed. Age is recorded after injury but fixed before it; heart rate on arrival is fixed after |
| `role` | `id`, `treatment`, `covariate`, `stand_in`, `after_treatment`, `observation`, `negative_control`, `restriction` | How the analysis uses it |
| `reason` | text, may be empty | The declared response; required where section 4 says so |
| `sensitivity` | text, may be empty | For a `stand_in`: the analysis that leaves it out |

A column that is both a restriction variable and a covariate gets its covariate role; the restriction use is read from the plan **[call]**.

The dictionary is stored in the lock and included in the lock hash. Rows are sorted by `column` before hashing, so row order does not change the hash **[call]**.

## 4. Rules

### 4.1 The lock refuses (error; no declaration rescues it)

1. **Missing or extra rows.** A kept column without a dictionary row; a row naming a column not in `design_data`; duplicate rows; a value outside the allowed set.
2. **Role mismatches.**
   - A column in `covariates` whose role is not `covariate` or `stand_in`.
   - A `covariate` or `stand_in` row that is not in `covariates`.
   - The treatment or id column with another role.
3. **A covariate fixed after time zero.** Role `covariate` with `fixed = "after"`. The message names the column and offers the three legitimate routes:
   - leave it out;
   - declare it `after_treatment` (P2 will use it as a node after treatment);
   - declare it `stand_in` with a reason and a sensitivity analysis.

   This catches payment, distance, the hospital reached, arrival-time covariates and the missing-measurement indicators for arrival physiology (rows 11, 13, 14, 15).
4. **Design columns from the follow-up source.** Any row with `follow_up = TRUE` whose role is neither `observation` nor `negative_control`. This catches the protocol's follow-up-call covariates (row 10). A negative-control outcome taken from the follow-up interview, such as function before the injury (`rescueCo_analysis` review M6), is allowed with a `reason`, because it is observed only for patients reached and so reveals who was followed up (section 4.2) **[call]**.
5. **Nodes after treatment in the adjustment set.** Role `after_treatment` or `observation` with the column in `covariates`. Rule 2 already catches this; it gets its own message because it is the common mistake.
6. **A treatment not assigned at time zero.** The treatment row with `fixed` other than `at`. A treatment fixed after the declared time zero means time zero is misplaced, which is the misalignment target trial emulation exists to prevent; the remedy is to move time zero, not to declare a response.

### 4.2 The lock requires a declared response (error if missing)

| Flag | Where the response goes | Rescue.Co example |
|---|---|---|
| `stand_in` covariate (fixed after time zero, adjusted for as a stand-in for something before it) | `reason` and `sensitivity` in its row | Arrival state in the D5 sensitivity analysis |
| `observation` column (an outcome-observation indicator in the design data) | `reason`: the approval, for example "D3, 2026-10-18; see blinding ledger" | Disposition recorded; six-month status recorded |
| Negative control from the follow-up source | `reason` | A pre-injury function item from the six-month interview |
| `restriction` variable fixed after time zero | `reason` | Direct arrival (transfer), which depends on route (row 3) |
| Eligibility criterion assessed after time zero | `response` in the plan's `eligibility` entry | Arrived alive (I1); the response cites the D6 bias analysis and restriction |
| Follow-up counted from an event other than time zero | `time_zero$response` in the plan | Six months from arrival, time zero at injury (row 30, I2) |

The lock checks that each response is non-empty text. It cannot judge whether the response is adequate; the dossier shows it to the approver.

### 4.3 Listed without a response (notes in the identification table)

- Covariates recorded after time zero but fixed before it, grouped by variable, for example age, sex, injury severity score, head injury severity. The declaration is the analyst's claim and is shown so the approver can dispute it. An optional `reason` is shown if given.
- A treatment recorded after time zero, for example transport recorded at arrival.
- Negative controls fixed after time zero, which is expected for negative-control outcomes in the strict sense.
- `after_treatment` columns, which are kept in the lock for P2 and out of the adjustment set.

## 5. The identification table

`design_report()` adds `identification`, a data frame rendered as a new dossier section, "Identification: what the plan declares", placed before "Design". It follows the components of a target trial emulation:

| Component | Declared | Flag | Response |
|---|---|---|---|
| Time zero | event; `measured_as` if given | | |
| Start of follow-up | `follow_up_from` | if it differs from time zero | `time_zero$response` |
| Eligibility (one row per criterion) | description; assessed before/at/after | if after | its response |
| Treatment | column, source, when recorded; fixed at time zero (rule 6) | note if recorded after | |
| Adjustment set: fixed before time zero | count of variables; recorded-after list | note | |
| Adjustment set: stand-ins | one row per variable | flag | reason; sensitivity |
| Nodes after treatment (not adjusted for) | one row per variable | note | |
| Outcome-observation indicators in the design data | one row per column | flag | reason (approval) |
| Restriction variables fixed after time zero | one row per variable | flag | reason |
| Negative controls | timing | note if fixed after | |

The table's caption says what a feasible verdict does and does not mean. The simulation says whether an estimator can recover the estimand if identification holds; this table, the negative controls and any bias analysis speak to whether it holds.

Each flag also becomes a row of the Muntner log (`export_design_log()`), at stage "Identification", with the flag as the issue, the response as the rationale, and the lock's creation time as the date.

## 6. Compatibility

- A lock made by 0.4.x has no dictionary. The lock hash includes the dictionary and `time_zero` only when they are present, so a 0.4.x lock still verifies (with the existing version warning) instead of failing with a misleading hash mismatch **[call]**. Every verb that takes a lock (`assess_design()`, `simulate_design()`, `negative_control_ladder()`, `design_report()`, `unblind()`, `estimate_effect()`) calls one internal guard that stops on a lock without a dictionary: "This lock was made by an earlier cleanTMLE; re-lock with a variable dictionary." This follows the existing guards on objects from older versions **[call]**.
- `cr_example` gains a `dictionary` element (a fourth data frame in the list, so no new exported object) and the `time_zero` its vignette plan uses: time zero at treatment assignment; `transfer` a restriction variable fixed before; `health_seeking` a negative control fixed before.
- Both vignettes and every example and test that builds a plan or a lock gain `time_zero` and `dictionary`. A test helper builds a default dictionary for test fixtures **[call]**, so tests stay short. The helper is internal and is not offered to users, because a generated dictionary would defeat the check.

## 7. Tests first

Written before the code, on simulated data, in `tests/testthat/test-lock.R`, `test-plan.R` and `test-dossier-unblind.R`:

1. `analysis_plan()` stops without `time_zero`; accepts a string and `measured_as`; stops when `follow_up_from` differs and `response` is missing or empty; stops on an eligibility criterion assessed after time zero without a response; rejects `assessed` values outside before/at/after.
2. `create_analysis_lock()`:
   - stops without `dictionary`;
   - stops on each failure in 4.1 (including a treatment row not fixed `at`, and a follow-up covariate, but not a follow-up negative control with a reason), with a message naming the column;
   - stops on each missing response in 4.2;
   - accepts each response.
3. Hash:
   - the dictionary is in the lock hash, so changing a timing after locking fails `verify_lock()`;
   - reordering the dictionary's rows does not change the hash;
   - a lock made without a dictionary (as by 0.4.x) still verifies, and every verb that takes a lock stops on it with the re-lock message.
4. A simulated cohort built like Rescue.Co's problems: a covariate recorded at disposition, an arrival measurement, a follow-up-call covariate, a route-based restriction, and an eligibility rule applied on arrival. The lock refuses the first three as covariates and requires responses for the last two. With them declared correctly, `design_report()` builds an identification table with exactly the expected flags and notes, and `export_design_log()` has one Identification row per flag.
5. `cr_example` locks with its shipped dictionary and the vignette plan, and the full pipeline (assess, simulate, controls, dossier, unblind, estimate) runs as before. Its estimates do not change, because P1 changes no estimation.
6. The rendered dossier (HTML) contains the identification section. This is a snapshot test, skipped when Quarto is absent, as the existing render tests are.
